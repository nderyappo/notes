Шпаргалка. Процесс разработки в продуктовой команде

1. Планирование и аналитика (От идеи к задаче)
Все начинается с исследования потребностей пользователей или бизнеса. [1]
* Product Manager (PM) или Product Owner собирает гипотезы, формулирует требования и оценивает их ценность.
* Business Analyst (BA) помогает детализировать требования, а Tech Lead или архитекторы продумывают техническую реализацию.
* Задача попадает в бэклог (список дел) в виде User Story или Task (например, в Jira или Яндекс.Трекере). [1, 2, 3]

2. Проектирование и дизайн
* UX/UI-дизайнеры создают макеты и интерактивные прототипы в Figma.
* Команда оценивает трудозатраты (story points), чтобы понять, сколько времени займет задача.
* Макеты утверждаются, а затем «декомпозируются» (разбиваются на более мелкие подзадачи для фронтенда, бэкенда и тестирования). [1, 2]

3. Написание кода и Code Review
* Разработчики (Developers) создают ветку (branch) в системе контроля версий (например, Git / GitLab / GitHub) специально для этой задачи.
* Пишется код, добавляются тесты (Unit-тесты).
* После завершения работы разработчик создает Pull Request (PR) или Merge Request — запрос на добавление своего кода в основную ветку продукта.
* Другие разработчики (тимлид или сеньоры) проводят Code Review (проверку кода) на наличие ошибок и соответствие стандартам качества. [1, 2, 3]

4. Сборка и тестирование (QA)
* Система непрерывной интеграции CI/CD (например, GitHub Actions, Jenkins, GitLab CI) автоматически собирает код и запускает тесты.
* Собранная версия деплоится (развертывается) на тестовый сервер (stage / dev).
* Тестировщики (QA-инженеры) проверяют новую функциональность вручную или запускают автоматические тесты.
* Если найдены баги, задача возвращается разработчику. Если все отлично, задача получает статус «Готово к релизу» (Ready for release). [1, 2, 3, 4]

5. Релиз (Выпуск в паблик)
Код готов к показу пользователям. Релиз может происходить по-разному: [1]
* Непосредственный выкат: Обновление "заливается" на боевые сервера (production) — пользователи получают новый функционал сразу.
* Фиче-тогглы (Feature Flags): Функционал выкатывается в код, но остается скрытым для пользователей. Менеджер продукта включает его удаленно (тумблером), когда это необходимо.
* A/B-тестирование: Функцию показывают только небольшой доле пользователей, чтобы сравнить показатели (конверсию, вовлеченность) со старой версией. [1, 2]

6. Мониторинг и поддержка
После релиза начинается сбор метрик. [1, 2]
* Аналитики смотрят, как нововведение влияет на поведение пользователей.
* Команда мониторинга отслеживает технические ошибки с помощью специальных систем (Sentry, Datadog), чтобы оперативно исправить непредвиденные проблемы. [1, 2, 3]
